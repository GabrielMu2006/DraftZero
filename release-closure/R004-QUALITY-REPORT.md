## 3. 诊断（P1，两类错误分开归因）

### 3.1 recall miss（4 个，全部英文稿）

4 个 miss 稿（`agent_eval_notes`、`note-app-features`、`podcast_episode_outline`、`sourdough schedule`）的真伙伴对**双向都不在队列中**。用 spike 向量核对：这些伙伴对合成分 0.579–0.632，**全部通过地板**——落选原因不是分数不足，而是**全局贪心双边截断的查询不对称**：zh 稿被 zh-zh 高分对占满 6 槽后，涉及它的中分段对（含跨语言伙伴对）在贪心循环中被整条跳过，另一端（英文稿）也因此失去该候选。分语言伙伴级统计：zh↔zh 伙伴 42 对中 41 对进 top-5；en↔zh 13 对全部进不了 top-5；en-en 伙伴对全部不在队列。"英文文件名"不是原因，正文语言与贪心截断交互才是。

### 3.2 precision 错误（基线 23 个 top-3 错例槽：en-en 12 + zh-zh 11）

字面分量（0.3 权重）对**任何同语言对**都有 ~0.02–0.10 的系统性加分（中中/英英共享高频字词），而跨语言真伙伴字面恒为 0 → 真伙伴被同语言噪声对稳定压过。生产证据：`agent_eval_notes ↔ tax checklist`（无关，sem 0.850 + lit 0.019 → 0.602）排在真伙伴（sem 0.866 + lit 0 → 0.606 量级）之前或将其挤到 top-3 之外。spike 诊断矩阵同样显示 e5+literal（75.8%）劣于纯语义（78.8%）。

## 4. 生产改动（P1）

`Core/Sources/DraftZeroCore/Semantic/CandidateEngine.swift`：

1. **保留规则**：全局贪心双边截断 → **每份草稿保留自己的前 K=6（并集）**，"每稿前 K 候选"的产品语义得以成立。
2. **排序权重**：`semanticWeight 0.7→1.0`、`literalWeight 0.3→0.0`（合成分=纯语义）；字面信号**不删除**——仍用于证据共同术语/标题命中展示、指纹与 0.98 重复阈值；地板合并为语义 ≥0.45。未按语言身份加任何固定分（A-005 路径不变，DeepSeek 仍不参与）。
3. **固定并列打破规则（P0 要求）**：`rankOrder`（combined→semantic→literal→pairKey）、队列 SQL `ORDER BY score DESC, draftA, draftB`、候选组聚合并列按 id——字典迭代顺序与 SQLite 并列顺序不再随进程随机。

**新回归测试**（`CandidateEngineTests`，9/9 通过；仅覆盖本次实际出错的行为）：

- `testSaturatedHubKeepsCrossLanguagePartnerPair`：枢纽稿满槽后跨语言伙伴对仍须在队列（旧贪心算法下该测试场景必然失败——伙伴对合成分低于 6 个同语言对，贪心双边截断双端都丢）。
- `testCrossLanguagePartnerRanksAboveSameLanguageNoise`：同语言噪声对字面分不得反转真伙伴排序。
